# 跨境订单分布式事务协调器

下单时同时扣仓储库存、订干线车位、预占关税额度、记一笔结算。四步跨四个系统，
任何一步失败都必须把前面的退回去。本项目是一个 Go 实现的协调服务：

- **TCC**：先对每个分支预留（Try），全部成功再确认（Confirm），任一失败全部取消（Cancel）。
- **Saga**：按编排顺序执行，失败后按**相反顺序**补偿。
- **防悬挂**：取消先于预留到达时做空回滚，并留下墓碑，迟到的预留请求被拒。
- **并行/顺序收尾**：确认与取消可按业务声明并行发，也可按声明顺序逐个发。
- **结果未知时的退避重试**：网络超时/5xx/连接断开一律视为“结果未知”，按指数退避持续重发，
  直到参与方给出明确结果；幂等键保证重发安全。
- **全局超时**：准备阶段超过全局截止时间自动回滚。
- **人工裁决**：卡死事务可由运维在页面上裁决为成功或失败，裁决后照常驱动分支收尾并留痕；
  参与方永久不可达时可“强制裁决”，按最后已知状态落账并标记为部分生效。
- **排查台**：全局事务、分支事务、补偿记录、悬挂检测、统计五个分区，外加实时事件流。
- **模拟验收**：四个模拟服务随机超时、报错、乱序、重启，跑几万笔下单，最后逐笔核对
  “要么四方全部生效，要么四方全部撤销”，并核对四方账本与协调器一致。

## 快速开始

```bash
# 协调器 + 四个模拟服务 + 排查台
go run ./cmd/coordinator -addr 127.0.0.1:8080
# 浏览器打开 http://127.0.0.1:8080/
```

```bash
# 2 万笔下单 + 混沌 + 人工裁决演练 + 逐笔对账（约 10 秒）
go run ./cmd/simulator -n 20000 -c 64 -chaos 1 -drill=true -timeout 1500 -report /tmp/report.json
```

单元测试（含 TCC/Saga、空回滚防悬挂、未知结果重试、超时回滚、人工裁决三条路径）：

```bash
go test ./... -count=1
```

## 结构

```
cmd/coordinator     协调器主程序（可内嵌四个模拟服务）
cmd/simulator       压测与核对程序
internal/engine     TCC/Saga 协调状态机
internal/store      内存状态 + 原子快照（-data 可持久化）
internal/transport  参与方调用与结果三分类（成功/确定失败/未知）
internal/sim        仓储、运力、关务、结算四个模拟服务
internal/sdk        业务方接入 SDK
internal/web        HTTP API + 排查台
wire/               协调器与参与方之间的协议
```

## 协议

所有分支操作都是 `POST`，请求体 `wire.Request`：

```json
{"txn_id":"txn-...","branch_id":"br-...","service":"warehouse",
 "biz_id":"CB-000001","seq":0,"amount":1200,"payload":{"hs_code":"8517.62"}}
```

`(txn_id, branch_id)` 是参与方的幂等键，也是防悬挂的栅栏。响应：

```json
{"ok":true,"outcome":"RESERVED"}
{"ok":false,"retryable":true,"code":"DB_BUSY"}
{"ok":false,"code":"REJECTED","outcome":"OUT_OF_STOCK"}
```

- `ok=true`：已生效（或幂等地早已生效）。
- `retryable=true` 或 HTTP 5xx/超时/连接断开：**结果未知**，协调器退避重发。
- 其余 `ok=false`：确定失败，不再重试。

参与方状态机（`internal/sim/participant.go`）：

| 操作 | 已预留 | 已确认 | 已取消（墓碑） |
|---|---|---|---|
| Try | 幂等成功 | 幂等成功 | **拒绝：ALREADY_CANCELED** |
| Confirm | 确认 | 幂等成功 | 冲突 |
| Cancel | 取消 | 冲突 | 幂等成功 |
| Execute | — | 幂等成功（已执行） | **拒绝：ALREADY_CANCELED**（已补偿） |
| Compensate | 空回滚（记墓碑） | 补偿 | 幂等成功 |

空回滚既返回成功，也在参与方留下墓碑；墓碑让迟到的 Try 无法落地——这就是“不能留下悬挂的预留”。

## 协调器不变量

1. **方向唯一且不可逆**：事务进入 `COMMITTING`/`ROLLING_BACK` 后方向锁定，任何分支都不会同时
   收到 Confirm 与 Cancel。运维也不能把已锁定的方向翻过来。
2. **“未知”不等于成功**：确认/取消/补偿只有拿到明确成功才算完成，否则一直退避重试；
   因此不会出现“车位订了钱没扣”这种靠猜结果造成的烂账。
3. **不跳过可能持有资源的分支**：准备阶段超时（结果未知）的分支一定会收到取消；准备阶段被明确
   拒绝的分支也会收到一次取消（空回滚），用于刷新墓碑。
4. **全有或全无**：正常路径下每笔事务要么全部分支生效，要么全部分支撤销。唯一的例外是运维的
   强制裁决，此时事务被标记为 `partial`，页面上明确显示“部分生效”，不会伪装成正常提交。
5. **收尾顺序**：Saga 的补偿按声明逆序；TCC 的取消同样逆序。并行模式下才允许同时发。
6. **可恢复**：状态是持久化的（`-data` 下原子快照），协调器重启后扫描未完成事务继续驱动。

## 排查台

- **全局事务**：每笔事务的状态、模式、分支进度条、**卡在哪个分支**、补偿次数、重试次数、耗时；
  卡死事务可直接打开“裁决”。点任意一行看分支明细、逐次调用记录、操作审计、四方账本核对。
- **分支事务**：按服务/状态筛选，看预留次数、收尾次数、补偿成功次数、最后错误。
- **补偿记录**：每次确认/取消/补偿调用一条，含结果未知后的每次重试与退避时长。
- **悬挂检测**：参与方账本的悬挂预留、被 fencing 拒绝的迟到预留、空回滚计数，以及协调器侧
  已结束但分支未决的异常。
- **统计**：提交/回滚/待裁决/空回滚/补偿/超时、状态分布、参与方账本、协调器计数器。

## 验证口径

模拟器最后做四类核对，任何一类不满足即判 FAIL：

1. **逐事务全有或全无**：已提交事务在四个服务都有效果；已回滚事务在四个服务都没有效果。
2. **金额一致**：每个服务记录的金额等于下单时的金额。
3. **四方集合一致**：四个服务“仍然生效的订单集合”完全相同，且等于协调器已提交数。
4. **无悬挂**：所有事务收尾后，四个服务的活跃预留为 0。

一次 2 万笔的典型结果：

```
事务=20006 已提交=19749 已回滚=257 待裁决=0 进行中=0
空回滚=510 补偿执行=1031 重试=2168 迟到预留被拒=1
四方生效订单集合一致: 19749 笔（协调器已提交 19749 笔）
结论: PASS
```

## 接入 SDK

```go
c := sdk.NewClient("http://coordinator:8080")
tx, err := c.Begin(sdk.TCC("ORDER-123").
    Branch("warehouse", 1200, nil).
    Branch("carrier", 800, nil).
    Branch("customs", 350, nil).
    Branch("settlement", 2350, nil).
    WithTimeout(2 * time.Second).
    WithParallel(true))
res, err := tx.Wait(ctx, 25*time.Millisecond) // 等待终态
```

业务方只需按 `wire` 协议实现三个（TCC）或两个（Saga）幂等端点，并用
`(txn_id, branch_id)` 做幂等与防悬挂——与 `internal/sim` 的做法一致。
